# Flicksy.VideoEditor — multi-clip editor

Detailed map for the **Flicksy.VideoEditor** exe. Part of the [architecture index](../ARCHITECTURE.md); the shared rendering/undo/media primitives it builds on live in [drawing.md](drawing.md). Section numbers are local to this file. Update this file (not the index) when the video-editor structure changes — see [CLAUDE.md](../../CLAUDE.md).

Shell stage — process boots, parses args, routes to Welcome or the editor shell, and initializes FFmpeg. The shell is a top toolbar + 5-column body (rail · panel · center · panel · rail). The center column has Preview + Transport stacked above a Timeline that renders the document's tracks/clips and a playhead overlay (visual layout: [video-editor/TIMELINE.md](../video-editor/TIMELINE.md)). Future code will reuse Drawing for per-clip annotation work.

## 3. Document model

Project document lives in [Flicksy.VideoEditor/Project/](../../Flicksy.VideoEditor/Project). JSON-serializable POCOs — no `Brush`/`Geometry`/`MatrixTransform` on any public property. The only allowed reference into Drawing is `DrawingItem` (held by `GraphicsClip`). Shape and rationale: [ADR 0002](../adr/0002-video-editor-document-model.md).

Timeline positions and clip durations are integer frames at `ProjectSettings.Framerate`. `MediaClip` source-time is `TimeSpan` (source-framerate-independent).

## 6. Shell layout

[VideoEditorWindow.xaml](../../Flicksy.VideoEditor/Windows/VideoEditorWindow.xaml) is the only editor window. Two rows: custom title bar (32) + body (star). An [OverlayHost](../../Flicksy.VideoEditor/Controls/OverlayHost.xaml) sits after the body in the root grid spanning both rows — the window-wide modal layer bound to `VideoEditorViewModel.OverlayHost` (§5).

The title bar is custom chrome: `WindowChrome` on the window (`CaptionHeight=32`, `UseAeroCaptionButtons=False`, `GlassFrameThickness=-1`) replaces the native frame so the menus can sit beside the title; the strip itself is [TitleBarView](../../Flicksy.VideoEditor/Controls/TitleBarView.xaml) bound to [TitleBarViewModel](../../Flicksy.VideoEditor/ViewModels/TitleBarViewModel.cs) (see §4/§5 — Undo/Redo and Project Settings are wired; the other menu commands are intentionally empty placeholders). Interactive title-bar children opt out of caption dragging via `WindowChrome.IsHitTestVisibleInChrome`. The window's root grid takes `Margin=8` when maximized so content isn't clipped by the maximized window's off-screen frame overhang. Body is 5 columns: left rail (44 fixed) · left panel (`x:Name="LeftPanelColumn"`, 280 default, MinWidth 0) · center (`*`, MinWidth 320) · right panel (`x:Name="RightPanelColumn"`, same) · right rail (`x:Name="RightRailColumn"`, 44 default, MinWidth 0). Both panels host all five stub controls stacked in the same `Grid`, each toggled visible by `EnumToVisibilityConverter` against the corresponding `CurrentXxxTab` value.

Only the left panel is user-resizable. Its `GridSplitter` is a direct child of the outer body grid (not nested inside the panel content) — a splitter only resizes its direct parent grid's columns. Placement: `Grid.Column="1"`, HorizontalAlignment=Right, default `BasedOnAlignment` resize behavior, which combined with the alignment picks the splitter's own column + the next (so dragging shrinks the panel and grows the center, or vice versa). Splitter `Visibility` is bound to `IsLeftPanelOpen` so a collapsed panel hides its splitter. The right panel is fixed-width (280) — no splitter. The center column has three outer rows: Preview (`*`, MinHeight 200), a horizontal `GridSplitter` (`Auto`), and a Transport+Timeline sub-grid (`2*`, MinHeight 200). The sub-grid stacks Transport (`Auto`) above Timeline (`*`, MinHeight 160); grouping them this way means the splitter resizes Preview vs the whole bottom block, and Transport keeps a fixed height while Timeline absorbs the remainder.

[VideoEditorWindow.xaml.cs](../../Flicksy.VideoEditor/Windows/VideoEditorWindow.xaml.cs) owns the panel collapse logic. Binding `ColumnDefinition.Width` to a converter would have worked for toggle, but `GridSplitter` writes `Width` directly on drag — that would clobber the binding. Instead, the code-behind subscribes to `ViewModel.PropertyChanged` for `IsLeftPanelOpen`/`IsRightPanelOpen` and writes the column `Width` itself: for the left panel, collapse stashes the current `Width` in a private field (so a drag-resized value is preserved) and sets `Width=0`, expand restores from the stash. The right panel always toggles 0 ↔ 280 since it can't be resized.

The right rail itself is also code-behind-managed (`ApplyRightRailState`): it expands to 44 only when the selected clip is a **`MediaClip`** (its Speed/Audio/… inspectors are media-only); otherwise — no selection, or a `GraphicsClip` selected — the column collapses to 0 and `IsRightPanelOpen` is forced false. A `GraphicsClip`'s style is edited from the left Shapes/Text panels (#13); its transform inspector is #15.

## 7. Composition

Backend-agnostic layer planning lives in [Flicksy.VideoEditor/Composition/](../../Flicksy.VideoEditor/Composition). Pure timeline math with zero Skia / WPF dependency so it can be tested in isolation from any render backend. Full design rationale: [ADR 0004](../adr/0004-compositor-design.md).

| File | Purpose |
| --- | --- |
| [CompositionLayer.cs](../../Flicksy.VideoEditor/Composition/CompositionLayer.cs) | Pure-data record struct: `(Clip, Track, ZIndex, SourceTime)`. One per active clip per frame. Carries the owning `Track` so the compositor can read `Kind` (paint-vs-mix routing) and `Muted` (audio-only skip) without re-walking the project. |
| [CompositionPlanner.cs](../../Flicksy.VideoEditor/Composition/CompositionPlanner.cs) | Static class. `PlanFrame(project, frame) → IReadOnlyList<CompositionLayer>` walks `Project.Tracks`, skips `Disabled` tracks, finds active clips (`[TimelineStart, TimelineStart + Duration)` half-open), and emits an ordered layer list. **Ordering**: Video tracks (lowest z) → Overlay tracks → Audio tracks. Within each visual kind, **reverse** document order — the top-most track in the UI (lowest index) paints LAST and ends up on top of the visual stack (Photoshop layer-panel convention, NOT Premiere's V1-below-V2). `Muted` is NOT filtered here — audio-only, applied by the compositor's mix pass. Exposes `IsActiveAt(clip, frame)` and `ComputeSourceTime(clip, frame, framerate)` publicly so callers (and tests) can reuse the math. Speed mapping: `SourceTime = SourceIn + ((frame - TimelineStart) / Framerate) * Speed` for `MediaClip`; `TimeSpan.Zero` for `GraphicsClip`. |
| [AudioBuffer.cs](../../Flicksy.VideoEditor/Composition/AudioBuffer.cs) | Output of `IAudioMixer.RenderAudio`. Sealed record carrying interleaved stereo float32 (`[L0, R0, L1, R1, …]`) and the sample rate. One video-frame's worth per call (`SampleRate / Framerate` stereo frames); `FrameCount` is `Samples.Length / 2`. |
| [ICompositor.cs](../../Flicksy.VideoEditor/Composition/ICompositor.cs) | Backend-neutral **video** seam. `RenderFrame(project, frame, target, frames?, plannedLayers?)` paints into a caller-owned `WriteableBitmap` (its size sets the render scale — full-res for export, sub-res for preview quality per ADR 0008; reused across frames, unfrozen → same-thread presentation). | [IAudioMixer.cs](../../Flicksy.VideoEditor/Composition/IAudioMixer.cs) | Audio seam split from `ICompositor` (ADR 0005). `RenderAudio(project, frame) → AudioBuffer` (`SampleRate / Framerate` stereo frames). NUnit 4. The compositor itself is not unit-tested — Skia + WPF + FFMediaToolkit interop is integration-test territory; the planner-side math is where regressions land cheaply.

## 8. Playback

Real-time playback lives in [Flicksy.VideoEditor/Playback/](../../Flicksy.VideoEditor/Playback). Threading + audio design: [ADR 0005](../adr/0005-playback-threading-and-audio.md); off-thread video decode-ahead: [ADR 0009](../adr/0009-decode-ahead-pump.md). Compositing runs on the UI thread, but the per-frame video **decode** runs ahead on a background pump so the tick only composites already-decoded frames (drops to the previous frame on a miss — never a UI stall). Paused **scrubbing** decodes off the UI thread too, through a coalescing [ScrubController](../../Flicksy.VideoEditor/Playback/ScrubController.cs) (random-access seeks are ~120 ms — far too slow to run on the dispatcher). A/V sync is system-clock master — video timed off a `Stopwatch`, audio pushed open-loop; both resync on every play / pause / seek / scrub.

| File | Purpose |
| --- | --- |
| [PlaybackEngine.cs](../../Flicksy.VideoEditor/Playback/PlaybackEngine.cs) | Owns the clock + audio output. `Play`/`Pause`/`StepFrame`/`TogglePlayPause`. A `Stopwatch` on a `CompositionTarget.Rendering` hook (only hooked while playing) computes `frame = _baseFrame + elapsed × framerate` each tick and writes it to `TransportViewModel.Playhead` (under a suppress flag so its own write isn't mistaken for a seek) — the preview repaints off that change, so video composites on the UI thread with no cross-thread hand-off. End-of-timeline holds the last content frame (`TotalFrames-1`) and pauses; Play-from-end restarts at 0. On play it **prebuffers** — the clock and audio are held at the start frame until the pump has the first frame decoded (`HasReadyFrameAt`, capped by `MaxPrimeWaitMs`), so video, playhead, and audio begin aligned rather than the playhead racing a cold decoder. While paused, a **debounced background prefetch** (`OnPrefetchTick` → `VideoPrefetchPump.Prefetch`) warms the pump at the settled playhead + preview scale so the next play reuses a hot buffer; the pump therefore keeps running while paused (a bounded buffer is held). Subscribes to `Transport.Playhead` so any **external** change (scrub, ruler/timeline click) **pauses playback if running** — a manual seek is a take-over — then re-bases on the new position and warms the prefetch for the next Play (frame step pauses on its own first). Owns the `AudioMixer` and the [VideoPrefetchPump](../../Flicksy.VideoEditor/Playback/VideoPrefetchPump.cs) (starts/stops/seeks it with playback, points the preview at it via [IPlaybackFrameSink](../../Flicksy.VideoEditor/Playback/IPlaybackFrameSink.cs)); disposed by `VideoEditorViewModel`. |
| [CompositorSampleProvider.cs](../../Flicksy.VideoEditor/Playback/CompositorSampleProvider.cs) | NAudio `ISampleProvider` adapting the per-frame `IAudioMixer` to the device's arbitrary-count pulls: mixes one frame at a time, serves slices, advances its own frame counter (the open-loop audio clock). `Read` runs on the device thread (the only caller of `RenderAudio`); `SeekTo(frame)` (UI thread) stores a `volatile` pending frame applied at the next `Read`, so the mixer is never touched cross-thread. |
| [VideoPrefetchPump.cs](../../Flicksy.VideoEditor/Playback/VideoPrefetchPump.cs) | Off-thread video decode-ahead (ADR 0009). A producer thread fills a bounded, **generation-stamped** `Queue<FrameBundle>` from an [IFrameBundleSource](../../Flicksy.VideoEditor/Playback/IFrameBundleSource.cs); the UI thread consumes via `BeginFrame(frame, scale)` / `EndFrame` and implements [IPlaybackFrameSource](../../Flicksy.VideoEditor/Playback/IPlaybackFrameSource.cs) (so it plugs straight into `ICompositor`). One `lock` guards `{queue, generation, nextFrame, scale, running}`, never held across a decode; `_current` is UI-thread-only. `Reprime`/scale-change = locked drain + generation bump (the producer self-cancels stale in-flight bundles at enqueue) — **not** `CompositorSampleProvider`'s lock-free `volatile` seek, which is unsafe across two threads sharing `ArrayPool` buffers. `Prefetch(frame, scale)` (start-or-`Reprime`) + `IsRunning` let the engine warm the pump while paused and reposition it on seek; `Reprime` (drain + generation bump + re-prime at an explicit scale) is the only seek entry point. The consumer takes the **newest ready frame ≤ playhead**; the producer decodes **strictly forward**, but once it trails the playhead by more than a **resync threshold** (the engine passes ~1 s of timeline frames) it jumps forward to the playhead in one seek (**bounded resync**), so a sub-realtime decoder drops frames with bounded A/V lag instead of freezing or drifting unboundedly behind the audio; a true miss holds the previous frame. `Dispose` joins the producer before disposing the source. |
| [FrameBundle.cs](../../Flicksy.VideoEditor/Playback/FrameBundle.cs) | One output frame's pre-decoded video: `{ Frame, Generation, Layers (planner snapshot), Frames (Clip.Id → VideoFrame, media layers only) }`. The snapshot lets the compositor render the exact planned set without re-walking the live project; the generation gates enqueue so no cross-epoch bundle is served. |
| [IFrameBundleSource.cs](../../Flicksy.VideoEditor/Playback/IFrameBundleSource.cs) / [ProjectBundleSource.cs](../../Flicksy.VideoEditor/Playback/ProjectBundleSource.cs) | The pump's decode primitive: `Produce(frame, gen, scale) → FrameBundle?` (null = skip, e.g. a torn `PlanFrame` mid-edit), `Recycle`, `TotalFrames`. `ProjectBundleSource` plans via `CompositionPlanner` and decodes each video layer through its own `DecodingFrameProvider`; the interface seam lets the pump be unit-tested against a fake (no FFmpeg/Skia/WPF). Used by both the pump and the scrub worker (`ScrubController`) — each holds its own instance + decoder cache (play and scrub are time-exclusive, so no thrash). |
| [IPlaybackFrameSource.cs](../../Flicksy.VideoEditor/Playback/IPlaybackFrameSource.cs) / [IPlaybackFrameSink.cs](../../Flicksy.VideoEditor/Playback/IPlaybackFrameSink.cs) | Source = the consumer face of the pump (`IClipFrameProvider` + `BeginFrame`/`EndFrame`/`CurrentLayers`) that `PreviewViewModel` drives. Sink = the set-only handle (`PlaybackFrames`) `PreviewViewModel` exposes so the engine can point it at the pump on play and clear it on pause. |
| [IPlaybackController.cs](../../Flicksy.VideoEditor/Playback/IPlaybackController.cs) | `TogglePlayPause` / `StepFrame(delta)` — the transport-facing surface `TransportViewModel` delegates to. Interface so the transport takes no hard dependency on the engine (and falls back to direct playhead manipulation in tests). |
| [ScrubController.cs](../../Flicksy.VideoEditor/Playback/ScrubController.cs) | Off-thread, coalesced **scrubbing** (paused seeks). A capacity-1 `DropOldest` `Channel` (newest target wins) feeds a background worker that decodes via its own `ProjectBundleSource` and `InvokeAsync`-dispatches the bundle back to `PreviewViewModel.PresentScrubFrame` (UI thread) to composite, then recycles it. The dispatch never blocks the worker, so `Dispose`'s join can't deadlock. Mirrors PostSnip's `VideoPlaybackOverlay` scrub worker; keeps the ~120 ms random-access seek off the UI thread (composite stays on it, ~0.5 ms). Owned + disposed by `PreviewViewModel`. |
| [BundleFrameProvider.cs](../../Flicksy.VideoEditor/Playback/BundleFrameProvider.cs) | Adapts one pre-decoded `FrameBundle` to `IClipFrameProvider` so a scrub-worker-decoded frame composites without re-decoding: `Acquire` serves the bundle's frame for a clip, `Release` no-ops (the controller recycles the whole bundle). |

Audio output: WASAPI shared mode via NAudio [WasapiOut]. The provider runs at the project sample rate; the engine queries the default render endpoint's mix rate ([MMDeviceEnumerator]) and inserts a `WdlResamplingSampleProvider` when it differs (shared mode needs a device-accepted format). Audio is best-effort — any init/start failure (no device, multichannel-only mix format) is caught and playback continues video-only.
